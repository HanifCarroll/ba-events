# Instagram publisher

A VPS job drafts four recurring posts for @baeventos.app from the catalog, and publishes them after they pass automated review in auto mode or Hanif explicitly approves. Only drafts that need approval get a Slack preview. It uses the Instagram Graph API (`graph.facebook.com`) unless Hoy's optional Business Suite link stickers are on. The token is the system-user token of the Meta app "BA Eventos Publisher" (id 2298370517615574, business portfolio HC Studio), made with Facebook Login for Business, because new Meta apps no longer offer Instagram Login. The specification is `openspec/specs/instagram-publishing/spec.md`. Post and preview copy lives in `src/features/instagram-publisher/copy.md`, and alert copy lives in `src/features/instagram-publisher/alerts.ts`.

| Format | Draft id | Kind | Events | Draft time | Instagram slot | Instagram approval cutoff | Instagram deadline | Threads slot → cutoff |
|---|---|---|---|---|---|---|---|---|
| Hoy | `hoy-YYYY-MM-DD` | story, 1080 × 1920 | today from 18:00, 2–4 | daily 11:00 | 17:00 | 17:00 | 19:00 | 11:30 → 17:00 |
| Este finde | `finde-<Friday>` | carousel, 1080 × 1350 | Friday–Sunday, 4–6 | Wednesday 18:00 | Thursday 12:00 | Friday 18:00 | Friday 18:00 | Thursday 12:00 → Friday 12:00 |
| Gratis esta semana | `gratis-<Monday>` | carousel, 1080 × 1350 | Monday–Sunday, free, 5–8 | Sunday 18:00 | Monday 12:00 | Tuesday 20:00 | Tuesday 20:00 | Monday 12:00 → Tuesday 12:00 |
| Este finde Reel | `reel-<Friday>` | reel, 1080 × 1920 MP4 with music | Friday–Sunday, 4–6, the carousel's selection minus events over by Friday 18:00 | Thursday 18:00 | Friday 12:00 | Friday 18:00 | Friday 18:00 | — |

The Instagram approval cutoff is the last moment a ✅ counts. At the Instagram deadline or the Threads cutoff, that channel stops making new writes and only reconciles requests it already sent.

All times are Buenos Aires (UTC−3).

Set `slack.channel` in `~/.config/ba-events/instagram-publisher.json` to override the default approval channel, #alerts (`C0CG3EGKKP1`). The publisher saves the channel with each preview, so changes affect only new previews. Previews already sent or handed to Slack without a saved channel keep using #ba-eventos (`C0CHBCSEV3R`) for lookups, approvals, and replies. Keep the old channel available until those drafts and their replies settle.

## Commands

Run from `~/projects/ba-events` on the VPS:

```sh
mise exec -- bun scripts/instagram-publisher.ts status
mise exec -- bun scripts/instagram-publisher.ts dry-run hoy --date 2026-11-21 --out /tmp/hoy --threads
mise exec -- bun scripts/instagram-publisher.ts dry-run finde --date 2026-11-20 --out /tmp/finde --threads
mise exec -- bun scripts/instagram-publisher.ts dry-run gratis --date 2026-11-23 --out /tmp/gratis --threads
mise exec -- bun scripts/instagram-publisher.ts threads-report --days 28
mise exec -- node --experimental-transform-types scripts/instagram-publisher.ts review hoy-2026-11-25 --dry-run
mise exec -- bun scripts/instagram-publisher.ts dry-run reel --date 2026-11-20 --out /tmp/reel     # renders the real MP4 (about 75 s)
mise exec -- bun scripts/instagram-publisher.ts regenerate finde-2026-11-20 --exclude <event id>
mise exec -- bun scripts/instagram-publisher.ts regenerate reel-2026-11-20 --track <track id>      # keeps exclusions; --exclude works too
mise exec -- node --experimental-transform-types scripts/instagram-publisher.ts tick               # what the timer runs
mise exec -- node --experimental-transform-types scripts/instagram-publisher.ts stickers-dry-run hoy-2026-11-19 --out /tmp/hoy-stickers
```

`dry-run` takes the run's first day (any day for Hoy, a Friday for Este finde and the Reel, a Monday for Gratis) and writes the frames, `caption.txt`, the Slack text in `slack.txt`, and `events.txt` (the picks with their ids). It never calls Slack, R2, Instagram, or Threads. For Hoy and the carousels, it also writes the exact `threads.txt` when Threads is enabled or `--threads` is passed. For the Reel it writes `reel.mp4`, `cover.jpg`, and `timing.json` instead of frames, says which track it chose, and takes `--track <id>` to try another. `regenerate` keeps earlier exclusions, posts a new preview only if the rebuilt draft needs approval, and resets any ✅. Every preview thread keeps its ❌ veto across rebuilds. When a rebuild needs no preview, it sends rebuild and outcome replies to the latest visible thread. It refuses a draft that's publishing or published on Instagram, or past its Instagram cutoff.

## How a tick works

The `ba-events-instagram.timer` user timer runs `tick` every 10 minutes. systemd never starts a second run of a oneshot service while one is still running, and a lock directory also guards against a manual `regenerate` racing a tick.

1. It checks the Instagram token (below).
2. For each due format whose cutoff hasn't passed, it creates a draft if none exists: it reads the catalog, picks the events, renders into `rev-1/`, and reviews the exact revision. Too few events is a logged skip. It shares a preview only when Instagram or Threads needs approval. An event-only review flag can go to the investigator first if neither destination is manual.
3. It delivers any reply still pending for an existing preview.
4. It reads Hanif's reactions on every shown preview with `reactions.get` (`approval.ts`). A ❌ on any of them stops both destinations, even after a rebuild. A ✅ only applies to the destinations and content revision that message showed. At the slot, publishing requires an in-time ✅ or a passing review and auto mode in both the saved revision and live config. If all eligible posts can publish automatically and no preview exists, the draft needs no Slack calls. An unreadable preview or unclear share makes the decision unknown. The job waits before replacing a preview, rebuilding, or starting new publication writes. If Slack fails before a preview is shared and the earlier previews are readable, the other destination can still publish automatically. If auto mode turns off before the cutoff, the draft requests approval. Older previews without saved modes still need a ✅. For Instagram a ✅ first seen by the tick just after the cutoff still counts if the deadline allows it, because Slack doesn't timestamp reactions.
5. Publishing verifies the frames against the saved revision. The Graph API path uploads them to R2 and runs `instagram.ts`. When Hoy link stickers are enabled, it tries Business Suite first (see below).
6. **Before every Instagram write** (each container, the carousel, each `media_publish`, each story frame), including retries of a draft already in `publishing`, the job re-checks approval and the clock, reading reactions only when a preview exists. Before the first new write of each attempt (every tick that writes), it also re-reads the selected events' status and times from D1 and checks them against the current time. An event that is no longer scheduled holds the draft with "Held: {title} was cancelled. Ask Hermes to regenerate it." An event that has ended (or started, with no end time) holds it with "Held: {title} has already happened. Ask Hermes to regenerate it." The alert explains whether a rebuild is still possible. Reconciling an earlier unclear publish is only a read, so none of these checks block it. ❌ ends the draft ("Skipped: you reacted ❌"). A removed ✅ (auto mode off) pauses it until the ✅ returns. At or after the deadline nothing new is created ("Skipped: not published by {HH:MM}"). If some story frames already went out, the draft is marked `failed` with an alert, and nothing more is posted.
7. It saves the outcome and queues a Slack reply only under an existing preview. If Slack fails, the outcome stands and later ticks retry the reply without publishing again.

Each failed attempt goes in the service log. Operational alerts still go through the shared alert system to #alerts and put the outcome and next step first, using Buenos Aires times. The final line has the draft ID and any diagnostic or command Hermes needs.

| Alert key (after `ba-events/instagram/`) | When it opens |
|---|---|
| `tick` | An item fails across three consecutive ticks, or a failing run still has no preview at least an hour after its draft time. The thread updates only when the qualifying draft IDs or their causes change. |
| `draft/<id>` | Publishing fails three ticks in a row, fails with less than an hour left, or gives up. A hold, a partial post that cannot continue, an interrupted rebuild, or a preview that misses its cutoff also alerts immediately. |
| `draft/<id>/slack` | The outcome message fails to send three ticks in a row. |
| `draft/<id>/review` | A revision still has no valid review in the last 30 minutes before its first eligible channel's slot or later. Hermes checks the reviewer. |
| `review-fix/<event id>` | A review finds a wrong field. Hermes checks the intake evidence and fixes the catalog or the publisher. A post-wide problem uses `draft/<id>/review-fix`. |
| `draft/<id>/threads` | Threads ends in `failed` or a fresh catalog check holds it, even if there was no preview. The job saves the affected event and reason for a hold and retries a failed alert command on the next tick. |
| `token` | Instagram token refresh fails, the token file is invalid, or a dated token has fewer than 10 days left. |
| `threads-token` | The Threads token refresh fails, the token file cannot be read, or the token still has at most 10 days left. |

A draft's alert streak counts failed ticks across steps, so changing from a reaction read failure to a publish failure doesn't reset it. The first alert's thread follows the draft across steps, while a final publish failure gets a draft alert. Publishing retries every tick. After six publishing failures the draft is marked `failed` unless a `media_publish` result is still unclear, in which case the job keeps checking it. The alert streak resets when publishing pauses; the six-failure retry budget does not. When a preview misses its cutoff or a rebuild stops part-way, the job won't publish the draft. A successful retry closes the open alert with a ✅ line. If the draft ends skipped, held, or failed, the alert names that outcome rather than claiming recovery. The alert command has up to three minutes for normal alerts. The publisher queues review fix alerts separately so an alert failure can't block a corrected draft.

## Automated review

The publisher reviews each new revision before deciding whether to send a preview, even in manual mode. An automatic post held by review can still publish without ✅ if review clears; the preview explains that when it exists. The OpenAI Responses API receives the rendered cover, event cards, closing frame, Instagram caption, and exact Threads text, if present. For a Reel it gets the cover and stills extracted from the saved video during the card holds. The reviewer gets the saved catalog fields and linked public intake caption and flyer, preferring a venue or organizer post and its cited slide. Retained flyers come from the private `baeventos-intake-evidence` bucket using the Cloudflare token; an expired original CDN URL may leave the reviewer with caption evidence only. The publisher never sends credentials or other private state in the model input, and requests `store: false`. Edit `src/features/instagram-publisher/review-prompt.md` to tune the factual, scope, and legibility checks.

- **All OK:** the publisher saves the model and verdicts with the revision, frame hash, exact-copy hash, and timestamps, and replies `Revisado: sin problemas.` only if there is a preview thread. Auto mode still needs both the saved revision and live config to allow it. Previously sent previews are unchanged.
- **Flagged event:** `wrong` and `question` both go to the investigator below. Automatic sends wait, but the investigator runs without a Slack preview. If it clears the facts or a rebuild can fix them, no decision preview is needed. Reviews saved before this change keep their old behavior.
- **Post-wide issue:** the investigator cannot clear it. Hermes still gets confirmed issues, and Hanif gets any unresolved decision about the post itself. The job broadcasts the question from the current preview thread to its channel (#alerts by default) if Hanif hasn't reacted and approval is still open. React ✅ or ❌ on the preview itself, not on the reply.
- **Unavailable:** the job logs a safe error and retries on later ticks. It alerts Hermes starting 30 minutes before the first applicable slot. A result that no longer matches the revision also blocks auto mode; regenerate rather than editing draft JSON. An in-time ✅ can override a missing, `question`, or `wrong` review, but never a ❌, an event hold, or a publishing deadline.

Add a private OpenAI project key as plain text at `~/.config/ba-events/openai-review-key` (mode `600`, owned by the publisher user). The default model is `gpt-6.2-sol`. The following optional config object shows the defaults; merge it into the existing config without changing other fields:

```json
{"review": {"model": "gpt-6.2-sol", "keyFile": "~/.config/ba-events/openai-review-key"}}
```

The review has no off switch for new drafts. Before updating the VPS checkout, provision the key, verify the Cloudflare token has R2 read access to `baeventos-intake-evidence`. Pause the timer and let any running service finish before updating the checkout. Run the review command against a saved still preview to check the key, R2 evidence, and model access, then restart the timer. No new timer is needed.

`review <draft id>` and `review <draft id> --dry-run` both call the configured model and print a fresh JSON verdict. They do not save it, send messages, rebuild, or publish. Use a saved preview with its frames still on disk; Reels rendered before this change have no saved card sample times and must be regenerated if you need to review them. Paid model calls are not part of contributor checks.

### Investigator

The 10-minute tick saves `request.json` under `drafts/<id>/investigation-<revision>/` and starts a transient systemd user service without waiting for Pi. Only one service can be requested per revision. It uses `openai/gpt-6.2-sol` at high thinking on the VPS user's Pi login, with 1000 MB and no swap. It stops at the earlier of 30 minutes from handoff or 20 minutes before the earliest still-open approval cutoff. The job checks the result on its next tick, not while the unit is running. Slack ✅ and ❌ take precedence and stop the investigation when seen; the original publishing and catalog checks still apply.

Pi has one allowlisted tool with operations for saved evidence, read-only catalog lookups via `bin/ba-d1-read.sh`, public HTTPS page and search reads, the guarded correction command, and private notes and findings. It has no general shell, filesystem access, Slack, or social writes. Public pages or search can block anonymous access. Treat search snippets as leads, not proof. The runbook is `scripts/publisher-investigator/prompt.md`.

- **All flagged events resolved as `ok`:** allow auto mode only for the exact reviewed revision, frames, and copy, and only if the post verdict is also `ok`.
- **`fixed` or `exclude` with no `ask`:** rebuild through `regenerate`, keep earlier exclusions, add explicitly excluded IDs, and quick-review the new preview. If a confirmed error cannot be corrected by the command, exclude the event and send the evidence and requested fix to Hermes. The two-rebuilds-per-draft-per-Buenos-Aires-day limit and the format minimum still apply. A draft can investigate at most twice across its revisions.
- **Any `ask`:** keep the current preview on hold, even if other events were fixed. The decision reply includes the question and the places checked, even if Hermes also gets a separate fix request. The job broadcasts it from the current preview thread only while approval is open and Hanif hasn't reacted. It saves the reservation before sending and never broadcasts twice for the same draft, even after a lost Slack response or a rebuild. A draft with an older notification already reserved does not broadcast again.
- **Missing, invalid, or late findings, or a unit failure:** nothing auto-publishes. Before the run ends, a missing result needs two consecutive unsuccessful unit checks before the job treats it as a crash. The job alerts Hermes under `ba-events/instagram/investigator` without broadcasting the infrastructure failure. The original preview is still eligible for a valid ✅. The job posts one plain line per flagged event for a completed investigation or fallback.

```sh
mise exec -- node --experimental-transform-types scripts/instagram-publisher.ts investigate <draft-id> --dry-run
mise exec -- node --experimental-transform-types scripts/instagram-publisher.ts investigate <draft-id>
```

Both commands require a saved quick review with flagged events. The dry run prints what would be queued (or the existing investigation) without launching Pi, applying fixes, sending messages, or writing state. The live command queues the same investigation the timer would, subject to reactions, time, and the round cap. It does not start a second run of the same revision.

`catalog-fix <event-id> --field <field> --from <value> --to <value> --evidence <URL-or-note> [--all-occurrences]` works only within an active investigation (`BA_INVESTIGATION_DIR` points to its directory) and only for a flagged intake event. Allowed fields are `description_display_es`, `description_display_en`, `description_summary_es`, `description_summary_en`, `name`, `starts_at`, `price`, `is_free`, and `status` (`scheduled` → `canceled` only). `null` means SQL NULL; times are UTC ISO timestamps with milliseconds, and the price is whole pesos. `--all-occurrences` requires the same title, venue, and linked source post, limits a change to 40 scheduled rows, and refuses the whole set if any old value or row changed. A clock correction keeps each occurrence's Buenos Aires calendar day. Title and admission changes rebuild the canonical `search_document` and queue vector maintenance; display and summary edits do not change the raw descriptions search uses. Existing scope invalidation still applies to title and admission corrections, so the next preview may omit a row until the scope judge runs again.

The private run directory contains `evidence.json`, any Reel stills, Pi's `run.log`, one `*.result.json` per event, and `fixes.jsonl`. Each submitted operation logs its old and new values, evidence, target IDs, and operation UUID. Confirmed corrections also appear as `catalogFixes` in the draft JSON. Files under finished draft directories age out with their frames after 14 days. Pi sessions persist under `investigator-sessions/`, and `investigator-memory.md` holds short venue and source notes in the state root. If D1 did not acknowledge a write, don't retry it blindly: check the operation UUID in `publisher_catalog_fixes` and read the affected rows. Keep evidence, logs, and sessions private.

```sh
systemd-run --user --collect --wait -p MemoryMax=1000M -p MemorySwapMax=0 /usr/bin/true
pi auth check --provider openai
pi --list-models gpt-6.2-sol
```

If the account is not signed in, use `pi auth login openai` for that user. Stop `ba-events-instagram.timer`, let any active service finish, fast-forward the VPS checkout to reviewed `main`, and run `mise exec -- bun install --frozen-lockfile`. On the first real investigation, check the private run log, the preview reply, and the draft's recorded findings; if it corrects a row, read it back through `bin/ba-d1-read.sh` and match the operation UUID. Do not make a test correction to a production event. Set `DB_READ_ONLY=1` in a publisher unit override if you need to stop catalog corrections without enabling auto-publishing of unresolved drafts.

## Threads trial

Add this key to `~/.config/ba-events/instagram-publisher.json`. Threads is off if the key is absent. Once the token is ready and the preview text looks right, set `enabled` to `true`. The existing `ba-events-instagram.timer` handles the Threads slots; no new timer or service change is needed. Run the report before switching `enabled` off at the end of the 28-day trial. Let open sends and Slack replies settle first: disabling Threads pauses reconciliation and reply delivery, and the job keeps their saved state.

```json
{"threads": {"enabled": false, "auto": {"hoy": false, "finde": false, "gratis": false}}}
```

Use a long-lived Threads user token for `@baeventos.app` with `threads_basic`, `threads_content_publish`, and `threads_manage_insights`. Store it in `~/.config/ba-events/threads-token.json` (mode 600) with `access_token`, `account`, `obtained` (ISO timestamp), and `app_id`. The job verifies the handle with `/me`, refreshes a token more than seven days old before its 60-day expiration, and saves a successful refresh atomically. It uses in-process `fetch`; never put the token in an invocation or a log. `threads-report` runs only with Threads enabled, does not refresh the token or write draft state, and shows the follower count and one row per known published post in the requested window. A dash means the API didn't return that metric.

Hoy and carousel revisions save the exact Threads text and include it in the shared Slack preview if one is needed and Threads is still eligible. A ✅ covers Threads only if that message showed the current Threads text. If Threads was disabled when the message went out and later needs approval, the publisher sends a preview that asks only about Threads. Instagram's original ✅ still counts for its unchanged revision. A ❌ on either thread stops both channels even in auto mode. Threads has its own auto flags and uses the existing timer's first tick on or after its slot or a later ✅, strictly before its cutoff. It publishes without a ✅ only if the saved revision and current config allow Threads auto mode and the revision passes the review gate. It never backfills a revision prepared without Threads. The list uses the saved picks in chronological order and removes leading `@` from words in titles, venues, and barrios so it does not tag other accounts. To fit 500 code points, it first removes the latest pick from the day with the most picks, stopping at one pick per day or the format minimum. If the text is still too long, it shortens titles to 40 code points before dropping any more picks. If needed, it then drops the latest pick overall until the text fits or reaches the minimum: two for Hoy and three for each carousel. If the minimum still doesn't fit, Instagram continues without a Threads post.

The two channels save and retry independently. Threads doesn't need the Instagram token or R2; both paths check the saved picks against the current catalog before writing. Threads checks approval at or after its slot and rechecks the cutoff and `threads.enabled` before each write. It reads reactions only if a preview exists. Without a successful read of all shown previews, new writes wait in both modes. Turning Threads off during a tick stops new writes and keeps any saved container. It waits up to about a minute per tick for the same container, checks the publishing quota before creation and before publish, and saves the latest already-visible media IDs with the attempt before dispatch. When the send's outcome is unclear, later ticks look for a unique exact text match from the attempt's second onward, excluding those saved IDs. The job never matches on time alone or repeats an unclear send. It reports an unresolved send at the cutoff or one tick after the attempt, whichever is later, so an unclear Este finde send can take about a day to report. Definite failures retry on later ticks, up to six API failures or the cutoff for new writes; Slack read failures do not use that budget.

If a preview exists, the Threads outcome is a separate reply in its original thread. A Slack failure leaves the reply pending without repeating the Threads post:

- `Threads: publicado {permalink}`
- `Threads: omitido, no se publicó antes de las {HH:MM}.`
- `Threads: omitido, reaccionaste ❌.`
- `Threads: retenido, {title} cambió (se canceló, ya pasó o salió de la agenda).`
- `Threads: falló ({short reason}). Hermes lo revisa.`

## Regenerate

`regenerate` refuses a draft that has started publishing on Instagram or is past its Instagram cutoff. If a Threads send is confirmed or unclear, Threads was skipped or failed, or its cutoff has passed, the rebuild keeps any existing Threads state and original Slack thread. The new preview does not offer another Threads post in those cases. If Threads already published, the new preview says `Threads ya se publicó con la versión anterior.` The job first saves the draft as revision n+1 in state `rebuilding` with Instagram approval cleared, then renders into `rev-<n+1>/` (old frames are never overwritten) and sends a new preview only if the revision needs approval. If it stops before rendering finishes, the next tick marks the draft `failed` and raises its alert with the exact command to run again if the cutoff is still open. If the frames are saved and Slack's response was lost, the next tick checks whether the preview arrived before trying to upload again. If a share might have succeeded, the job waits for a successful lookup instead of uploading a replacement or treating the missing timestamp as permission. Each discovered preview keeps its veto, not its ✅ for changed content. The publisher reloads the saved draft before advancing it or delivering a pending reply, and refuses to save over a changed draft. Publishing uploads only frames that sit in the saved revision's directory and match its hash.

## The Reel

The Reel shows the Este finde selection again as a video: a cover card, one card per event, and a closing card, in the same flyer-led look as the still frames (see "Look and artwork"; the HyperFrames project is built in `src/features/instagram-publisher/reel/project.ts`). It picks by the carousel's rule, so an event without artwork is not dropped; its card shows the no-flyer tile. Its picks use the Este finde rules, leave out the finde draft's `--exclude` ids, and leave out any event that would be over by the Reel's Friday 18:00 deadline (its end, or its start when it has no end), so the pre-publish check never holds it at the slot or at a late ✅. So it shows the carousel's selection minus Friday daytime events, with the next picks filling their places; a 12:00–20:00 exhibition stays, a 12:00 talk with no end time doesn't. Each card holds still for H = max(3.0 s, 0.35 s × words, characters / 17) after a 0.5 s entrance and before a 0.2 s exit, rounded up to whole beats of the track, so every cut lands on a beat. A Reel is about 37 s with 4 events and 48 s with 6.

**Music.** The tracks live outside the repo, in the directory `reel.musicDir` in the config (default `~/.local/share/ba-events/reel-music`): one audio file per track and `tracks.json`, whose `tracks` entries have `id`, `title`, `artist`, `file`, `durationSec`, `bpm`, `startSec`, `credit`, `source`, and `license`. The Meta Sound Collection tracks may only be used in content on Meta's products and never distributed separately, and the repo is public, so never commit the files or anything made from them. `startSec` is a downbeat where the full arrangement plays, with enough music after it for the longest Reel (6 events with long titles, about 82–87 s) before the track ends or goes quiet. `bpm` comes from the kick, not from `hyperframes beats`, which can follow off-beats.

**Rotation.** A new Reel draft takes the track whose last published Reel is oldest; tracks never published come first, in `tracks.json` order. The draft saves its track, `regenerate` keeps it unless given `--track <id>`, and the preview's last line names it ("Music: …"). A track with a `credit` adds that line to the caption. A missing directory or file, a track without `bpm` and `startSec`, or a track whose `license` starts with "CC BY" but has no `credit`, fails the draft with the tick alert; there's never a Reel without music. The excerpt starts at `startSec`, fades in over 0.3 s and out over 1.0 s, and is normalized to −14 LUFS and −1.5 dBTP; the build refuses one that runs past the end of the file.

**Rendering.** `npx --yes hyperframes@0.9.66 render --quality delivery --workers 1` (telemetry off) runs in `systemd-run --user --scope --collect --unit=ba-events-instagram-reel-<pid>-<ms> -p MemoryMax=1000M -p MemorySwapMax=0 -p RuntimeMaxSec=600`; a timeout or error stops the scope. It uses HyperFrames' managed Chrome Headless Shell in `~/.cache/hyperframes/chrome/`, not Playwright's (which exits at once). If it's missing the draft fails with an alert naming `npx --yes hyperframes@0.9.66 browser ensure`; the VPS has no `unzip`, so that install needs an unzip shim on `PATH`. ffmpeg and ffprobe come from `BA_INSTAGRAM_FFMPEG_DIR`, `PATH`, or `~/.hermes/tools/ffmpeg-*/bin`. On the VPS the 48 s Reel took about 75 s and peaked at about 850 MB in its scope with the earlier text-only look; measure it again with flyers. Fonts, the logo (`static/logo.svg`), the flyers downloaded for this render, and GSAP (`node_modules/gsap`) are copied into the project; nothing is fetched at render time. During a card's hold only the flyer moves (a 4% zoom over the card's length); the words stay still. If a card's fonts don't load, the card still registers its timeline and prints `BA_REEL_CARD_FAILED` to the browser console, and the job fails the render when it sees that line, so a font problem fails in seconds and never produces a video in a fallback face. The job checks the MP4 (1080 × 1920 H.264 yuv420p at 30 fps with AAC, the expected length) before it's previewed.

**Publishing.** It uploads `instagram/<draft id>/<hash>/reel.mp4` (`video/mp4`) and `cover.jpg` (the cover card's hold frame) to R2, creates one `media_type=REELS` container with `video_url`, `cover_url`, `caption`, and `share_to_feed=true`, and polls its `status_code` for up to about 5 minutes per tick. A video still processing leaves the draft `publishing` without counting a failure, and the next tick polls the same container, but only after the same reaction and deadline check as a write: ❌ skips it, a removed ✅ pauses it, and the deadline ends it. After an unclear `media_publish`, the media id is looked up by exact caption among posts of the same kind (`REELS` for a Reel, `CAROUSEL_ALBUM` for a carousel), because the two often share a caption. The render's project directory, which holds the audio excerpt, is removed whether the render succeeds or fails. Then it checks `content_publishing_limit` and calls `media_publish`, with the same idempotency and checks as a carousel (below).

**Slack.** When the Reel needs approval, the preview is a new top-level message with the MP4 attached (through Slack's external upload, which sends the bytes straight to the upload URL; a 10 MB video is fine) and ends with `Music: "{title}" by {artist}.`

## Selection

Events come from the Instagram intake (they have `event_source_evidence`) and must be scheduled, not time-TBA, not all-day, not location-hidden, and have a venue with a barrio. An event that is over by the publish slot (its end, or its start when it has no end) is left out, so Sunday's Gratis draft doesn't list Monday-morning events. The pick is greedy and deterministic: one event per venue (names compared without accents or punctuation), a free event first for Hoy and Este finde when one qualifies, then whichever event has artwork (an `events.image_url` on one of the known image origins), adds a new barrio, a new category, and a description line, earliest first on ties. Artwork outweighs the other three together, but an event without artwork is still picked when no candidate with artwork is left. The cards are in start order.

Placeholder start times don't count as real ones: a 23:59 start (the intake's end-of-day stand-in), and a 00:00 start when an intake candidate (not a link to a scraped event) left `time` empty. Time-TBA rows are already `time_tba`. A title ending in "@ {venue}" (or "@{venue}") that names the event's own venue loses that suffix.

The tag is the venue's `instagram_handle`, else the account of the intake post the event came from, else none (the caption then names the venue). When the tag is the posting account and its name doesn't match the venue's (`accountIsVenue`: "salalucida" is Sala Lúcida, "ccmacedonia" is Centro Cultural Macedonia, "vamos_gratis" isn't Facultad de Derecho), the caption names the venue and ends the line "Vía @handle.", and the card footer reads "Vía @handle". "A la gorra" comes from the intake candidate's `price_note` when its `price_kind` is `conditional` and the note says "a la gorra", "contribución consciente", or "a voluntad"; the catalog has no column for it.

## Look and artwork

Every format uses the website's look (`look.ts`): its near-black ground `#101012`, the logo's coral `#e8484a` and paper `#fbf3e6`, the lime `#d0ff36` of its filter pills, Newsreader semibold for headlines, DM Sans for everything else, and the real logo (`static/logo.svg`) at the top left. No format uses a stock photo.

- **Event card.** The event's own flyer, whole (never cropped), over a blurred, darkened copy of itself, above a solid near-black panel with the kicker, title, description line, venue, barrio, price pill, and footer handle. The words never sit on the flyer. On a carousel the panel starts at a fixed seam. On a Hoy frame and in the Reel the blur fills the whole frame, the panel is a rounded box only as tall as its words, and the page sizes the flyer into the space between the logo row and the panel (`placeFlyers` in `look.ts`), so the link sticker's band and everything under the panel show the blurred flyer. Titles are fitted in the page to two lines with a size floor (`data-fit`), and cut with an ellipsis only at the floor.
- **No flyer.** An event without usable artwork gets the same card with a dark tile in the flyer's place: a coral rule and the title.
- **Covers.** The carousels and the Reel show the post's first three flyers as tilted, overlapping prints, like the site's header. The Reel's cover sets them on a blend of their blurred copies. The Hoy cover shows tonight's flyers in a grid that runs from the top of the frame to the bottom; the part behind and below the headline is dimmed. The headline is paper on a coral box with a lime date chip above it.
- **Closing.** A dimmed mosaic of the post's flyers behind the closing words.

Before a render, `artwork.ts` downloads each picked event's `image_url` next to the render directory. It connects only to the catalog's known image origins (`isArtworkOriginAllowed` in `src/features/events/lib/artwork-delivery.ts`: our R2 route `https://baeventos.com/api/event-artwork/<id>/<sha>.<ext>` and the listed CDN hosts and paths), because it runs on the VPS before anyone approves the draft. It follows at most three redirects by hand and checks each hop against the same list before requesting it; a disallowed address or hop is never requested. Then: 10 s for the whole download, at most 15 MB, and it must decode as a JPEG, PNG, WebP, GIF, or AVIF of at least 200 px. It saves a JPEG of at most 1280 px on the long side and a small blurred backdrop, one image at a time, and removes them when the render ends. Any failure is logged (`artwork: <id> (<title>) failed (<why>); using the no-flyer card`) and that event renders the no-flyer card; a flyer never fails a render. Only a broken setup does: if `sharp` doesn't load, the draft fails with a message that says to run `bun install`. The frames page sets `data-ready` once its fonts are loaded and its text is fitted, and the render fails if a vendored font or a local image didn't load, so a frame never goes out in a fallback face.

On a 1080 × 1920 frame the logo, counter, words, and footer stay between y 250 and 1670. In the Reel the words also stay left of x 916 and above y 1330, clear of Instagram's buttons and caption, and the cover's words sit inside the profile grid's centre 3:4 crop.

### Layout versions

Every new draft saves `layout` (`LAYOUT_VERSION` in `html.ts`), the version of the positions its frames were rendered with. The sticker preview, the Business Suite route, and the Graph tags all read it. A draft with no `layout` was rendered before the flyer-led redesign and keeps the earlier positions (`LEGACY_LAYOUT`: every link sticker at its old y, the mention at y 1618, and tags on the old footer line). An approved revision's frames are never rendered again in place. Bump `LAYOUT_VERSION` whenever a sticker, tag, or footer position moves, and keep the old positions readable for drafts that carry the old number.

A caption can't realistically pass Instagram's 2,200 characters: eight Gratis lines would need to average about 240 characters each. If one did, Instagram would reject the post, not publish a wrong one.

## Hoy link stickers

Set `"linkStickers": {"hoy": true}` in `~/.config/ba-events/instagram-publisher.json` to enable them. Leave it absent or `false` until you've reviewed a dry run and are ready to supervise the first approved Hoy. Carousels, Reels, and drafts already using Graph are unaffected.

Use the pinned Node version for `tick` and `stickers-dry-run`. The systemd unit uses Node with `--experimental-transform-types`, and the still-frame render child inherits that flag. After updating a checkout, run `systemctl --user daemon-reload` to pick up the tracked unit change (reinstall the unit first if it was copied rather than symlinked). Keep the existing Bun lockfile and install. On the VPS, the publisher gives `~/.agents/skills/remote-desktop/scripts/rbrowser pro url` 20 seconds to open or reuse the loopback tunnel at `http://127.0.0.1:9342`. If it cannot open the tunnel, the job falls back to Graph before Share. On the Pro the endpoint is `http://127.0.0.1:9333`; `BA_INSTAGRAM_STICKERS_CDP` can override either default. Meta must be signed in on the Pro's AgentBrowser. Never point this job at the LinkedIn or personal Chrome profile.

`stickers-dry-run` works with the flag off. It takes a saved Hoy draft with its original revision's frames still on disk. It uploads those frames into a new Business Suite composer tab, saves the Instagram preview as `frame-1.png`, `frame-2.png`, and so on in `--out`, discards the composer, and closes its tab. It never shares, schedules, calls the Graph API, or changes the draft. Use `BA_INSTAGRAM_STATE_DIR` to point to a private copy of a draft and its frames, with the saved paths updated to that copy.

Without an R2 bucket configured, the job does not start a new publish through either route. It still reconciles a saved Share attempt. The publisher opens its own Chrome target and uploads the JPEGs over that tab's DevTools connection. It does not attach to other tabs or change browser-wide settings. It then places the cover's **Ver la agenda** sticker and the closing frame's **Buscar planes** sticker on `https://baeventos.com`. Each event's **Ver evento** sticker goes to its event page. Business Suite edits each frame and uses **Share now** for `baeventos.app` only, not the Facebook Page. The job re-checks approval, time, and the catalog just before Share. The link-sticker route adds a native Instagram Mention for the same venue or curator account Graph would tag. Business Suite's smaller mention pill (at most 90 px tall) sits over the printed handle in the card's footer and covers nothing else. The footer row is centred at y 1432 with 32 px above it (to the barrio row) and below it (to the panel's end). On a curator's card "Vía" has its own cell left of the handle, and the site's address keeps the right end of the row. `mentionArea` in `html.ts` is the rectangle the pill must stay inside: after "Vía", before the address, under the barrio row, and above the link band. A pill that is too wide for it (a long username) is shrunk first, and a long handle's printed text shrinks from 36 px to as little as 32 px so the pill still covers it. After the drag the composer measures the pill's whole rectangle; if it is outside the area it places it once more, and if it is still outside, the composer is discarded before Share and the Story goes out through Graph. After placing each link sticker the composer measures it and requires it to lie wholly inside that frame's free band (`STICKER_BAND`; an event frame's is y 1484 to 1670, and its 160 px sticker is aimed at the middle, y 1577, with 13 px to spare on each side). If it doesn't, the composer is discarded before Share and the Story goes out through Graph, with the usual alert. The link stickers sit in bands the layout leaves empty (`STICKER_Y` in `html.ts`: centre y 1440 on the cover, 1577 on an event frame, 1390 on the closing frame). The publisher ignores lookalikes and display-name matches. If it can't find the exact username, it skips only that mention and lists the skipped usernames in the draft outcome note and, if there is a preview, its Slack reply (or prints them for a dry run).

If the composer fails, the error and any composer alert point to a private `composer-failure-*` directory. It contains `failure.json` with the failed step and last known page URL (without its query string), and `screenshot.jpg` if the tab was still reachable. If a DevTools command times out before the final Share checks, the publisher closes that tab and tries one fresh composer within the same six-minute limit. Look under `--out` for a dry run, or `drafts/<id>/` under the publisher's state directory for a live attempt. Keep those files private.

If Business Suite fails before the Share attempt, the job discards the composer and uses Graph subject to the usual checks. A successful fallback alerts under `draft/<id>/stickers` with the cause (including a lapsed sign-in) and the next step. The browser flow has a six-minute cap. After saving the Share attempt, the job never makes a second write for that draft, even if approval is withdrawn or the feature is turned off. The job checks Graph for exactly the expected number of new Story IDs in the five minutes after the attempt, excluding IDs seen before Share. It polls for about a minute after the click, checks on later ticks, and holds with an alert if it can't confirm by the deadline. Don't publish manually on the account in that five-minute window: Graph counts frames but does not identify their composer or verify their stickers.

## Graph API publishing and idempotency

Reels: see "The Reel" above. Carousels: one image container per slide (`is_carousel_item=true`, `user_tags` positioned on the footer handle), wait for `FINISHED`, then the `CAROUSEL` container with the caption, wait for `FINISHED`, check `content_publishing_limit`, and `media_publish`. Stories: one `media_type=STORIES` container per frame with a `user_tags` mention and no coordinates, each published in order.

Each container and media id is saved to the draft's state file before the next step. Just before `media_publish` the unit records `pendingSince`. If the call has no clear answer, the next attempt reads **that container's own** `status_code`: `PUBLISHED` means this attempt went out (a carousel's media id is then looked up by its exact caption; a story frame is recorded as published without one); `FINISHED` means it didn't, and the same container is retried (a container publishes at most once); `EXPIRED` or `ERROR` starts over; anything else holds with an alert. Recent media and stories never decide whether something was posted, so an unrelated story posted around the same time is never adopted. Reconciling reads don't need approval, so an unclear publish is still settled after the deadline or a ❌.

## State and files

- State: `~/.local/state/ba-events-instagram/drafts/<id>.json` (one per draft) and the rendered frames in `drafts/<id>/current/`. Frames of finished drafts are removed after 14 days; the state files stay.
- Config: `~/.config/ba-events/instagram-publisher.json`, for example `{"auto": {"hoy": false, "finde": false, "gratis": false, "reel": false}, "r2": {"bucket": "baeventos-instagram-media", "publicBaseUrl": "https://ig-media.baeventos.com"}, "reel": {"musicDir": "~/.local/share/ba-events/reel-music"}}`. Auto mode is off unless set to `true`, and `reel.musicDir` defaults to that path. Without `r2`, Instagram stays preview-only; Threads does not use it.
- Instagram token: `~/.config/ba-events/instagram-token.json` (mode 600) with `access_token`, `ig_user_id`, and `expires_at`. A system-user token never expires: write `"expires_at": "never"` and the job skips refreshing and the expiry warning. For a dated token, once the token is more than 7 days old (by `refreshed_at`, or the file's modification time) the job refreshes it with `refresh_access_token` and writes it back atomically. A failed refresh or fewer than 10 days left raises `ba-events/instagram/token`. Without the file the job drafts and previews, then logs that it skipped publishing.
- R2: frames go to `instagram/<draft id>/<hash>/frame-N.jpg` (a Reel's to `reel.mp4` and `cover.jpg`) through the Cloudflare API, using the token `bin/ba-d1-read.sh` reads (`~/.config/ba-events/cloudflare-deploy-token`). A bucket lifecycle rule deletes them after 7 days.
- Slack: `~/.hermes/skills/productivity/slack-workspace/scripts/slack_api.py` (it reads the bot token itself).
- Rendering: the Reel as above; the frames with Playwright's Chromium headless shell from `~/.cache/ms-playwright`, in a child process under `systemd-run --user --scope --unit=ba-events-instagram-render-<pid>-<ms> -p MemoryMax=900M -p MemorySwapMax=0 -p RuntimeMaxSec=170`. On a timeout or error the job runs `systemctl --user stop <unit>.scope`, so no Chromium process outlives the render.
- Secrets never reach a command line: `bin/ba-d1-read.sh` hands curl its Authorization header on stdin (`curl -K -`), R2 uploads and Instagram calls use `fetch` inside the process, and `slack_api.py` reads the bot token itself. Fonts are the local woff2 files in `src/features/instagram-publisher/assets/fonts/` (Newsreader and DM Sans, OFL-1.1, from Fontsource).

## Troubleshooting

- **No preview or repeated tick failures:** run `journalctl --user -u ba-events-instagram.service -n 50`. The current streaks are in `~/.local/state/ba-events-instagram/tick-failures.json`, including failures before a draft file existed. If that file can't be read, the job logs the error, tries to move it aside as `tick-failures.json.bad-<timestamp>`, and starts with empty streaks. A render timeout mentions low memory only if the job measured less than 600 MB available when the render failed.
- **Publishing or a Slack reply failed:** run `mise exec -- bun scripts/instagram-publisher.ts status` and read the draft JSON. Check the saved container IDs and `pendingSince` before taking any action on Instagram. A pending `notify` does not mean Instagram needs another attempt.
- **Held or interrupted rebuild:** use `mise exec -- bun scripts/instagram-publisher.ts regenerate <draft id> --exclude <event id>` before the cutoff if publishing hasn't started. Omit `--exclude` if the picks don't need to change. After the cutoff, don't rebuild or manually retry the old draft.
