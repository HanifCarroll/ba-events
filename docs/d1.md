# D1 baseline

BA Eventos is moving from Supabase to Cloudflare D1 in a series of PRs. Production stays on Supabase until the cutover. Until then the D1 schema is used only by tests, scripts, and the staging Worker.

## Schema

[`migrations/0001_baseline.sql`](../migrations/0001_baseline.sql) is the production Supabase schema as of 2026-11-16, hand-written for SQLite. It has all 28 production tables, the two views, and the triggers that still apply. Its header comment gives the type map. The main rules are:

- Every timestamp is the exact string `Date.prototype.toISOString()` writes (`2026-11-16T12:00:00.000Z`), and a CHECK refuses any other form. Never write `datetime()`.
- JSON and arrays are JSON text checked with `json_valid`, and enums are `CHECK IN`.
- Booleans are 0 or 1, and every table is `STRICT`.
- The app generates ids with `crypto.randomUUID()`.

These parts of the Supabase schema are not in the baseline:

- `auth.*` and `storage.*`. Better Auth and R2 replace them. Columns that referenced `auth.users` reference `profiles(id)` instead.
- Row-level security. Server code will check ownership itself.
- SQL functions. Later PRs port the ones still in use to TypeScript.
- Full-text, trigram, and vector indexes. Search moves to FTS5 and Vectorize (see [Search](#search)).
- The `mark-past-events` pg_cron job.

The migration is checked against production with a read-only script that loads every production row into a fresh local D1 database. Its result is in delivery PR 01.

### Triggers

SQLite triggers can't change the row being written. So each Postgres `BEFORE` trigger is an `AFTER` trigger that updates the row a second time. D1 leaves `recursive_triggers` off, so a trigger never fires itself, but it does fire the other triggers. RETURNING shows the row before these triggers ran.

- **`updated_at`.** Updates to `venues`, `events`, `user_preferences`, `import_blocklist`, `venue_review_queue`, and `conversations` set `updated_at` to the current time.
- **Intake protection** (`events_protect_intake_facts`). This is Postgres' `protect_intake_event_facts`, unchanged in behaviour. It applies when an update changes a column listed in the event's `event_intake_protection.fields`. It quietly puts that column back to its old value, and puts back `search_document` and `embedding_version` too. A scheduled event that has started may still become `past`.
- **Hidden location** (`events_hidden_location_has_no_venue_*`). An event with `location_hidden = 1` never keeps a `venue_id`. This rule beats intake protection.
- **Assistant message parent.** This is `validate_assistant_message_parent`.

## Search

Search runs on D1 only when the Worker binds `DB`. Each entry point (the SvelteKit hook and the MCP Worker) passes its env to `useCloudflareBindings` in [`search-bindings.server.ts`](../src/shared/lib/db/search-bindings.server.ts), and the reads in `client.server.ts` that `search_events` uses then call [`search-d1.server.ts`](../src/shared/lib/db/search-d1.server.ts) instead of Supabase. The covered reads are lexical, semantic, filter-only, count, happening-now, furthest date, and venue name. Venue-name lookup matches in TypeScript over the venue names, because SQLite's LIKE folds the case of ASCII letters only; like Postgres' ilike, it folds case (accented capitals too) but not accents.

- **Lexical.** [`migrations/0002_events_fts.sql`](../migrations/0002_events_fts.sql) adds `events_fts`, an external-content FTS5 index over `events.search_document`, `name`, and `description_es` with `unicode61 remove_diacritics 2`. Three triggers keep it in step with `events`, so writers never touch it. Rebuild it with `INSERT INTO events_fts(events_fts) VALUES ('rebuild')`. [`websearch-fts5.ts`](../src/shared/lib/search/websearch-fts5.ts) turns the query into an FTS5 expression with the meaning `websearch_to_tsquery` gave it. FTS5 finds and filters the matches (up to 1,000, best bm25 first), and `tsRankCd`, a port of Postgres' `ts_rank_cd`, orders them by the text Postgres ranked, then by start time, as before. Unlike Postgres' `simple` config, accents fold: "musica" finds "Música". The venue name Postgres appended to the text is already in every scheduled event's `search_document`.
- **Semantic.** The Vectorize index is `baeventos-events-staging` on staging, bound as `VECTORIZE` (1,536 dimensions, cosine). Each vector's id is the event id, and its metadata is `{ status, starts_at }`, with `starts_at` in epoch milliseconds. Both fields have metadata indexes. A query asks for the 100 nearest vectors with `status = 'scheduled'` and the date window, and D1 applies the other filters. Vectorize's scores are approximate, so the survivors are scored again by exact cosine similarity from their stored vectors (`getByIds`, 20 ids a call), and those above 0.2 are kept in that order. Whoever writes an event's status or start time must update its vector's metadata too.
- **List filters** reach SQL as one JSON array each, read with `json_each(?)`, so no query nears D1's limit of 100 bound values.
- **Venue similarity.** [`trigram.ts`](../src/shared/lib/search/trigram.ts) is a port of pg_trgm `similarity()`. It equals production Postgres on 500 real name pairs, captured with `bun scripts/capture-trigram-fixture.ts` (read-only) into `trigram.fixture.json`. [`venue-similarity-d1.ts`](../src/features/import/core/venue-similarity-d1.ts) has the D1 versions of `find_similar_venue` and `intake_similar_venues`. The importers and the intake switch to them with their D1 repositories in delivery PR 04 and PR 06.
- **Overlap with production.** `node --env-file=.env evals/search/backend-overlap.ts` runs 10 fixed queries against production's Supabase search and the staging D1 and Vectorize, and fails if any query is below 70% top-10 overlap for lexical search or 80% for semantic search. It compares only events whose status, start, and searched text are the same on both sides, and reports how many it left out, because staging drifts from production as importers write to it. It needs a Wrangler login and runs under Node, because Wrangler's remote bindings hang under Bun.

## Writing from server code

[`src/shared/lib/db/d1.server.ts`](../src/shared/lib/db/d1.server.ts) is the seam the later PRs build on.

- **`boundD1Database(env)`** returns the `DB` D1 binding of a Worker env or SvelteKit `platform.env`, or `null` when there is none. Code uses D1 only when this returns a database. Otherwise it keeps using Supabase, which is the case in production until the cutover.
- **`batchAssert(db, reason, condition, ...values)`** makes a statement for a `db.batch()`. If `condition` is false, the whole batch is rolled back and fails with `reason`. It works through the `_assert` table, whose rows are never kept.
- **`intakeCommitBatch(db, statements)`** wraps an intake commit. It sets the one-row `write_context` table first and clears it last, so intake protection lets the commit change protected facts. If the batch fails, nothing is kept, including the bypass. Hand-written fixes go the same way: insert `write_context` first and delete it last, in the same `wrangler d1 execute --file`.

## Tests

[`tests/support/d1.ts`](../tests/support/d1.ts) `freshD1()` starts an in-memory Miniflare D1 through Wrangler's `getPlatformProxy`. It applies every file in `migrations/` in order. Call it once per test file in `beforeAll`, and call `dispose()` in `afterAll`. It runs under both `bun run test` (Vitest) and `bun test` and needs no credentials. Miniflare enforces D1's real SQL authorizer and foreign keys.

[`src/shared/lib/db/d1-schema.test.ts`](../src/shared/lib/db/d1-schema.test.ts) covers the parts of the Postgres SQL tests in `supabase/tests/` that this schema owns: constraints, triggers, and views. The Docker Postgres tests (`scripts/test-instagram-intake-db.sh`) keep running until the cutover, because production is still on Supabase.

## Chat, guests, Telegram, feedback, and the rate limiter (PR 05)

[`src/shared/lib/db/d1-binding.server.ts`](../src/shared/lib/db/d1-binding.server.ts) holds the Worker's `DB` binding. The SvelteKit hook and the Telegram Worker's `fetch`, `alarm`, and `scheduled` record it with `useD1Binding(env)`, together with search's `useCloudflareBindings(env)`, so a Telegram turn stores and searches on the same backend. The jobs Worker's guest retention step reads the binding from its env directly. Code that finds a binding uses D1; code that finds none keeps using Supabase, which is production until the cutover.

- **Chat turns.** [`chat-d1.server.ts`](../src/features/chat/api/chat-d1.server.ts) ports `bootstrap_chat_turn`, `claim_chat_turn`, `complete_chat_turn`, `fail_chat_turn`, and `insert_message_with_turn` to single `db.batch()` calls. Row locks become `batchAssert` preconditions and guarded `UPDATE … WHERE`. Sequence and turn numbers are computed inside the insert statement, so concurrent writers can't share one. The error messages are the RPCs' own (`Turn conflict`, `Turn claim lost`, and so on).
- **Ownership.** D1 has no row-level security. Every chat function takes the signed-in user's id (from `event.locals.user`, which the session hook sets) and filters by it. Telegram's conversations have no user and are reached only through the `telegram` channel with `user_id IS NULL`.
- **Conversation search** matches every word of the query as a case-insensitive substring of a message, instead of Postgres' `websearch_to_tsquery`. The match runs in JavaScript over the user's own messages, because SQLite's `lower()` folds only ASCII and would miss "Ópera". That is enough for a few dozen conversations.
- **Rate limiter.** [`rate-limit-d1.server.ts`](../src/shared/lib/db/rate-limit-d1.server.ts) counts with one `INSERT … ON CONFLICT DO UPDATE … RETURNING` and deletes windows older than 7 days in the same batch. Chat stays at 50 an hour and the API at 10 a minute, and it still fails closed (3-second ceiling, then 503 or a chat error).
- **Guest lifecycle and debug rows, `/api/feedback`, and Telegram's `telegram_updates`, retention, and health** write the same rows to D1 that they write to Supabase.
- **Checking against staging data.** `node scripts/check-chat-d1-staging.ts` runs the chat, Telegram, and feedback readers against `baeventos-staging` through a wrapper that refuses anything but SELECT. It then exports the chat tables into a local Miniflare D1 and runs the write paths on the copied rows there. It prints counts only and exits 1 on any failure.
- **Sessions.** A D1-bound Worker has no sign-in until Better Auth (PR 07), so `getSessionUserEffect` returns signed out there and staging serves guests only.

## Catalog

The importers, venue settlement, the venue review queue, enrichment, the blocklist, and the daily-scrape audit write through one repository, `CatalogStore` (`src/features/import/core/catalog-store.ts`). `catalogStoreFor(env, supabase)` in `catalog-store-for.ts` picks `d1Catalog` when the env binds `DB` and `VECTORIZE`, and `supabaseCatalog` otherwise. A `DB` without `VECTORIZE` is refused, because new events would be unsearchable.

- **Decoding.** `catalog-store-d1.ts` decodes rows with Effect Schema (0/1 to booleans, JSON text to arrays and objects) and writes every timestamp with `toISOString()`. Inserts generate the id with `crypto.randomUUID()`.
- **Venues.** Same-name and fuzzy matching run over the venue list. The store keeps the list in memory, and before each lookup it reloads the list if the count, the newest rowid, or the newest `updated_at` of `venues` changed. That way a venue that one source's import creates is seen by the others, which run concurrently. Inside the list, `venueNameKey` replaces `venues_named`, and `trigramSimilarity` (`src/shared/lib/search/trigram.ts`, delivery PR 03) replaces `find_similar_venue`, with the same tie-break (oldest, then lowest id).
- **Vectorize.** The vector id is the event id, and its metadata is `{ status, starts_at }`, with `starts_at` in epoch ms. An event write with a new embedding upserts the vector. A write that changes `status` or `starts_at` rewrites the metadata and keeps the values, because Vectorize has no metadata-only update. When intake protection reverts the search document, the old vector stays, as the old embedding did in Postgres. Deleting events deletes their vectors. The D1 write comes first. A write with a new embedding also adds the event to `vector_sync` (`migrations/0003_vector_sync.sql`) in the same transaction, and removes it once Vectorize has the vector. If the Vectorize call fails, the event stays queued.
- **`mark-past-events`.** The hourly cron in `baeventos-jobs` (`src/jobs-worker/catalog-maintenance.ts`) runs the pg_cron rule from 20261114210000: an ended event, a timed event 4 hours after its start, or a date-only event 28 hours after its midnight start becomes `past`, and the vector's status follows.
- **Nightly reconcile.** At 03:00 Buenos Aires, it runs `reembed-stale` for scheduled events with an old or missing search document (queued in `vector_sync` the same way). It re-embeds each event still in `vector_sync` from its stored `search_document`, restores missing vectors of live events from their stored document, and rewrites metadata that differs from the row. It checks every event that isn't past or canceled, plus every event changed in the last 48 hours. At most 200 embedding calls run per night, and the rest is reported as `deferred`.
- Both crons do nothing without `DB`, so production keeps pg_cron until the cutover.

## Copying production

[`scripts/d1-migrate/`](../scripts/d1-migrate/) copies production Supabase into a D1 database, a Vectorize index, and two R2 buckets. Hermes runs it in the cutover. Until then it fills staging. Run it with `node` from the repo, because Wrangler's remote proxy hangs under Bun 1.3.14. Keep the run directory outside the repo with mode 700: it holds production data, including the 4 users' emails and about 1.1 GB of images.

```sh
RUN=/tmp/ba-copy-$(date +%Y%m%d-%H%M); mkdir -m 700 "$RUN"
node --env-file=.env scripts/d1-migrate/export.ts --dir "$RUN"     # about 7 minutes
node scripts/d1-migrate/transform.ts --dir "$RUN"                  # seconds
node scripts/d1-migrate/load.ts --dir "$RUN"                       # about 10 minutes
node --env-file=.env scripts/d1-migrate/verify.ts --dir "$RUN"     # about 4 minutes, exits 1 on any mismatch
```

- **`export`** reads production only. It uses PostgREST and Auth admin GETs, Storage object GETs, and Storage's list call, which is a read-only POST. It writes every row of the 28 tables to `raw/<table>.jsonl`, and stops if production has a table the tool doesn't list. It also writes the auth users' ids and emails to `raw/auth_users.jsonl` for the Better Auth import, and every `instagram-evidence` and `event-artwork` object, each checked against the sha256 in its key. `source-acquisitions` is a cache and isn't copied. If a table's row count changes while it is being paged, the table is exported again.
- **`transform`** applies the baseline's type map: booleans become 0 or 1, timestamps become `toISOString()` form (Postgres microseconds are cut to milliseconds), and jsonb and arrays become JSON text. It writes the embeddings to `vectors.ndjson` unchanged, with the event id as the vector id and metadata `status` and `starts_at` (epoch milliseconds). It rewrites each `events.image_url` in Supabase's `event-artwork` bucket to `https://baeventos.com/api/event-artwork/<event id>/<sha256>.<ext>`, which keeps the R2 key as the last segment. URLs in intake plan payloads are history and stay as they are.
- **`load`** empties every copied table in the target D1 and inserts the rows in batches of at most 500, in foreign-key order. The migrations must already be applied. It upserts the vectors in batches of 1,000, then deletes any vector whose id isn't an exported event. It puts each object into R2 with its sha256, which R2 checks, and skips objects already there with the same hash. `--only d1,vectorize,r2` reruns one part.
- **`verify`** checks that every table's D1 row count equals the export. It checks 100 events and 50 venues field by field against production after decoding, allowing only the artwork URL rewrite. It waits until the index holds exactly one vector per exported embedding and compares 100 sampled vectors with their metadata. It checks that every object is in R2 with its hash and size, and that no other objects are there. It also prints production's live counts. Those must match only with `--production`, because the cutover freezes writes and staging doesn't.

Every target defaults to staging (`--d1`, `--vectorize`, `--evidence-bucket`, and `--artwork-bucket`). The scripts refuse any target whose name doesn't end in `-staging` unless `--production` is passed, and only Hermes passes it, in the cutover. A rerun of `load` against staging removes whatever other PRs wrote there.

The new artwork URL form takes effect only when production moves to D1. Until then, today's artwork route accepts only the 320, 640, and 1280 WebP variants and Supabase's origin, so the plan PR that serves artwork from R2 has to serve `<sha256>.<ext>` from the artwork bucket and allow that URL form.
