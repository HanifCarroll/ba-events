# D1 baseline

BA Eventos is moving from Supabase to Cloudflare D1 in a series of PRs. Production stays on Supabase until the cutover. Until then the D1 schema is used only by tests, scripts, and the staging Worker.

## Schema

[`migrations/0001_baseline.sql`](../migrations/0001_baseline.sql) is the production Supabase schema as of 2026-11-16, hand-written for SQLite. It has all 28 production tables, the two views, and the triggers that still apply. Its header comment gives the type map. The main rules are:

- Every timestamp is the exact string `Date.prototype.toISOString()` writes (`2026-11-16T12:00:00.000Z`), and a CHECK refuses any other form. Never write `datetime()`.
- JSON and arrays are JSON text checked with `json_valid`, and enums are `CHECK IN`.
- Booleans are 0 or 1, and every table is `STRICT`.
- The app generates ids with `crypto.randomUUID()`.

These parts of the Supabase schema are not in the baseline:

- `auth.*` and `storage.*`. Better Auth and R2 replace them. Columns that referenced `auth.users` reference `profiles(id)` instead.
- Row-level security. Server code will check ownership itself.
- SQL functions. Later PRs port the ones still in use to TypeScript.
- Full-text, trigram, and vector indexes. Search moves to FTS5 and Vectorize.
- The `mark-past-events` pg_cron job.

The migration is checked against production with a read-only script that loads every production row into a fresh local D1 database. Its result is in delivery PR 01.

### Triggers

SQLite triggers can't change the row being written. So each Postgres `BEFORE` trigger is an `AFTER` trigger that updates the row a second time. D1 leaves `recursive_triggers` off, so a trigger never fires itself, but it does fire the other triggers. RETURNING shows the row before these triggers ran.

- **`updated_at`.** Updates to `venues`, `events`, `user_preferences`, `import_blocklist`, `venue_review_queue`, and `conversations` set `updated_at` to the current time.
- **Intake protection** (`events_protect_intake_facts`). This is Postgres' `protect_intake_event_facts`, unchanged in behaviour. It applies when an update changes a column listed in the event's `event_intake_protection.fields`. It quietly puts that column back to its old value, and puts back `search_document` and `embedding_version` too. A scheduled event that has started may still become `past`.
- **Hidden location** (`events_hidden_location_has_no_venue_*`). An event with `location_hidden = 1` never keeps a `venue_id`. This rule beats intake protection.
- **Assistant message parent.** This is `validate_assistant_message_parent`.

## Writing from server code

[`src/shared/lib/db/d1.server.ts`](../src/shared/lib/db/d1.server.ts) is the seam the later PRs build on.

- **`boundD1Database(env)`** returns the `DB` D1 binding of a Worker env or SvelteKit `platform.env`, or `null` when there is none. Code uses D1 only when this returns a database. Otherwise it keeps using Supabase, which is the case in production until the cutover.
- **`batchAssert(db, reason, condition, ...values)`** makes a statement for a `db.batch()`. If `condition` is false, the whole batch is rolled back and fails with `reason`. It works through the `_assert` table, whose rows are never kept.
- **`intakeCommitBatch(db, statements)`** wraps an intake commit. It sets the one-row `write_context` table first and clears it last, so intake protection lets the commit change protected facts. If the batch fails, nothing is kept, including the bypass. Hand-written fixes go the same way: insert `write_context` first and delete it last, in the same `wrangler d1 execute --file`.

## Tests

[`tests/support/d1.ts`](../tests/support/d1.ts) `freshD1()` starts an in-memory Miniflare D1 through Wrangler's `getPlatformProxy`. It applies every file in `migrations/` in order. Call it once per test file in `beforeAll`, and call `dispose()` in `afterAll`. It runs under both `bun run test` (Vitest) and `bun test` and needs no credentials. Miniflare enforces D1's real SQL authorizer and foreign keys.

[`src/shared/lib/db/d1-schema.test.ts`](../src/shared/lib/db/d1-schema.test.ts) covers the parts of the Postgres SQL tests in `supabase/tests/` that this schema owns: constraints, triggers, and views. The Docker Postgres tests (`scripts/test-instagram-intake-db.sh`) keep running until the cutover, because production is still on Supabase.

## Staging

The staging D1 is `baeventos-staging`, bound as `DB` in [`wrangler.staging.jsonc`](../wrangler.staging.jsonc). That config is for the staging Worker `baeventos-staging`, which later PRs fill in and deploy. CI never deploys it. Apply new migrations with:

```sh
bunx wrangler d1 migrations apply baeventos-staging --remote --config wrangler.staging.jsonc
bunx wrangler d1 migrations list baeventos-staging --remote --config wrangler.staging.jsonc
```

No production Wrangler config has a D1 binding until the cutover PR.

The other staging resources are the Vectorize index `baeventos-events-staging` (1,536 dimensions, cosine, metadata indexes `status` and `starts_at`) and the R2 buckets `baeventos-intake-evidence-staging` and `baeventos-artwork-staging`.

## Copying production

[`scripts/d1-migrate/`](../scripts/d1-migrate/) copies production Supabase into a D1 database, a Vectorize index, and two R2 buckets. Hermes runs it in the cutover. Until then it fills staging. Run it with `node` from the repo, because Wrangler's remote proxy hangs under Bun 1.3.14. Keep the run directory outside the repo with mode 700: it holds production data, including the 4 users' emails and about 1.1 GB of images.

```sh
RUN=/tmp/ba-copy-$(date +%Y%m%d-%H%M); mkdir -m 700 "$RUN"
node --env-file=.env scripts/d1-migrate/export.ts --dir "$RUN"     # about 7 minutes
node scripts/d1-migrate/transform.ts --dir "$RUN"                  # seconds
node scripts/d1-migrate/load.ts --dir "$RUN"                       # about 10 minutes
node --env-file=.env scripts/d1-migrate/verify.ts --dir "$RUN"     # about 4 minutes, exits 1 on any mismatch
```

- **`export`** reads production only. It uses PostgREST and Auth admin GETs, Storage object GETs, and Storage's list call, which is a read-only POST. It writes every row of the 28 tables to `raw/<table>.jsonl`, and stops if production has a table the tool doesn't list. It also writes the auth users' ids and emails to `raw/auth_users.jsonl` for the Better Auth import, and every `instagram-evidence` and `event-artwork` object, each checked against the sha256 in its key. `source-acquisitions` is a cache and isn't copied. If a table's row count changes while it is being paged, the table is exported again.
- **`transform`** applies the baseline's type map: booleans become 0 or 1, timestamps become `toISOString()` form (Postgres microseconds are cut to milliseconds), and jsonb and arrays become JSON text. It writes the embeddings to `vectors.ndjson` unchanged, with the event id as the vector id and metadata `status` and `starts_at` (epoch milliseconds). It rewrites each `events.image_url` in Supabase's `event-artwork` bucket to `https://baeventos.com/api/event-artwork/<event id>/<sha256>.<ext>`, which keeps the R2 key as the last segment. URLs in intake plan payloads are history and stay as they are.
- **`load`** empties every copied table in the target D1 and inserts the rows in batches of at most 500, in foreign-key order. The migrations must already be applied. It upserts the vectors in batches of 1,000, then deletes any vector whose id isn't an exported event. It puts each object into R2 with its sha256, which R2 checks, and skips objects already there with the same hash. `--only d1,vectorize,r2` reruns one part.
- **`verify`** checks that every table's D1 row count equals the export. It checks 100 events and 50 venues field by field against production after decoding, allowing only the artwork URL rewrite. It waits until the index holds exactly one vector per exported embedding and compares 100 sampled vectors with their metadata. It checks that every object is in R2 with its hash and size, and that no other objects are there. It also prints production's live counts. Those must match only with `--production`, because the cutover freezes writes and staging doesn't.

Every target defaults to staging (`--d1`, `--vectorize`, `--evidence-bucket`, and `--artwork-bucket`). The scripts refuse any target whose name doesn't end in `-staging` unless `--production` is passed, and only Hermes passes it, in the cutover. A rerun of `load` against staging removes whatever other PRs wrote there.

The new artwork URL form takes effect only when production moves to D1. Until then, today's artwork route accepts only the 320, 640, and 1280 WebP variants and Supabase's origin, so the plan PR that serves artwork from R2 has to serve `<sha256>.<ext>` from the artwork bucket and allow that URL form.
