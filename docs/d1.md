# D1 baseline

BA Eventos runs on Cloudflare D1, Vectorize, and R2. See the [cutover runbook](ops/d1-cutover.md) for the migration and service retirement history. A missing binding fails closed; there is no database fallback.

## Schema

[`migrations/0001_baseline.sql`](../migrations/0001_baseline.sql) is the production Supabase schema as of 2026-11-16, hand-written for SQLite. It has all 28 production tables, the two views, and the triggers that still apply. Its header comment gives the type map. The main rules are:

- Every timestamp is the exact string `Date.prototype.toISOString()` writes (`2026-11-16T12:00:00.000Z`), and a CHECK refuses any other form. Never write `datetime()`.
- JSON and arrays are JSON text checked with `json_valid`, and enums are `CHECK IN`.
- Booleans are 0 or 1, and every table is `STRICT`.
- The app generates ids with `crypto.randomUUID()`.

These parts of the Supabase schema are not in the baseline:

- `auth.*` and `storage.*`. Better Auth and R2 replace them. Columns that referenced `auth.users` reference `profiles(id)` instead.
- Row-level security. Server code will check ownership itself.
- The original SQL functions. Active operations now live in the D1 repositories.
- Full-text, trigram, and vector indexes. Search moves to FTS5 and Vectorize (see [Search](#search)).
- The `mark-past-events` pg_cron job.

The migration is checked against production with a read-only script that loads every production row into a fresh local D1 database. Its result is in delivery PR 01.

### Triggers

SQLite triggers can't change the row being written. So each Postgres `BEFORE` trigger is an `AFTER` trigger that updates the row a second time. D1 leaves `recursive_triggers` off, so a trigger never fires itself, but it does fire the other triggers. RETURNING shows the row before these triggers ran.

- **`updated_at`.** Updates to `venues`, `events`, `user_preferences`, `import_blocklist`, `venue_review_queue`, and `conversations` set `updated_at` to the current time.
- **Intake protection** (`events_protect_intake_facts`). This is Postgres' `protect_intake_event_facts`, unchanged in behaviour. It applies when an update changes a column listed in the event's `event_intake_protection.fields`. It quietly puts that column back to its old value, and puts back `search_document` and `embedding_version` too. A scheduled event that has started may still become `past`. The nightly stale-document repair uses the intake write context only for these two derived search fields, and only while the accepted inputs still match the ones it embedded. If the latest intake update reused its search document, the job also compares the stored document with a fresh local build at the current version before deciding whether to re-embed.
- **Hidden location** (`events_hidden_location_has_no_venue_*`). An event with `location_hidden = 1` never keeps a `venue_id`. This rule beats intake protection.
- **Assistant message parent.** This is `validate_assistant_message_parent`.

## Event scope

[`0005_event_scope.sql`](../migrations/0005_event_scope.sql) adds `scope`, `scope_reason`, `scope_judged_at`, and `scope_version`. `events.scope` is `'in'`, `'out'`, or NULL; public lists show only `'in'`. Direct event URLs, saved events, and authenticated catalog maintenance reads retain their existing behavior. Scope writes leave `events.updated_at` alone, so they do not invalidate intake plans. Edits to classification facts, venue name/barrio changes, and newly linked intake evidence clear the judgment. The classifier guards each write against the inputs it actually read.

The existing hourly mark-past task tries up to 200 scheduled events starting today or later in Buenos Aires, prioritizing recent changes. It calls OpenAI GPT-6 Luna in batches of 15 and logs counts only. Failed batches remain unjudged and retry later. Increase `SCOPE_VERSION` when revising the policy so older judgments become eligible again.

The operator backfill uses Node 24 (Bun does not support this Wrangler remote proxy reliably). Run it from the repo root with an authenticated Wrangler session that can access the chosen D1 database and a private env file containing `SCOPE_OPENAI_API_KEY` for that environment:

```sh
node --env-file="$HOME/.config/ba-events/scope-staging.env" scripts/event-scope.ts --staging --dry-run --limit 60 --report /tmp/ba-scope-staging-preview.json
node --env-file="$HOME/.config/ba-events/scope-staging.env" scripts/event-scope.ts --staging --apply --limit 60 --report /tmp/ba-scope-staging-apply.json
```

Use a fresh report path for each run. Without `--limit`, the command pages through all outstanding scheduled events starting today or later; judgments at the current version are skipped. `--dry-run` never writes D1. `--apply` re-judges whatever still needs a judgment, so it can differ from a preview; both modes report failures, and a nonzero exit or `complete: false` requires operator review. For production, replace `--staging` with `--production` and use the production operator env file. Keep reports outside the repo.

Production order: privately export D1 and record a Time Travel bookmark; let the merge's CI job apply the migration before deploying Workers; review the production dry-run, then apply. The public catalog can be sparse until scope fills in. For a code rollback, leave the additive columns in D1 and roll back the application and publisher together. Do not drop the columns or overwrite the catalog.

## Search

Search runs on D1 and requires the `DB` binding. Each entry point (the SvelteKit hook and the MCP Worker) passes its env to `useCloudflareBindings` in [`search-bindings.server.ts`](../src/shared/lib/db/search-bindings.server.ts), and the reads in `client.server.ts` that `search_events` uses then call [`search-d1.server.ts`](../src/shared/lib/db/search-d1.server.ts). The covered reads are lexical, semantic, filter-only, count, happening-now, furthest date, and venue name. Venue-name lookup matches in TypeScript over the venue names, because SQLite's LIKE folds the case of ASCII letters only; like Postgres' ilike, it folds case (accented capitals too) but not accents.

- **Lexical.** [`migrations/0002_events_fts.sql`](../migrations/0002_events_fts.sql) adds `events_fts`, an external-content FTS5 index over `events.search_document`, `name`, and `description_es` with `unicode61 remove_diacritics 2`. Three triggers keep it in step with `events`, so writers never touch it. Rebuild it with `INSERT INTO events_fts(events_fts) VALUES ('rebuild')`. [`websearch-fts5.ts`](../src/shared/lib/search/websearch-fts5.ts) turns the query into an FTS5 expression with the meaning `websearch_to_tsquery` gave it. FTS5 finds and filters the matches (up to 1,000, best bm25 first), and `tsRankCd`, a port of Postgres' `ts_rank_cd`, orders them by the text Postgres ranked, then by start time, as before. Unlike Postgres' `simple` config, accents fold: "musica" finds "Música". The venue name Postgres appended to the text is already in every scheduled event's `search_document`.
- **Semantic.** The Vectorize index is `baeventos-events-staging` on staging, bound as `VECTORIZE` (1,536 dimensions, cosine). Each vector's id is the event id, and its metadata is `{ status, starts_at }`, with `starts_at` in epoch milliseconds. Both fields have metadata indexes. A query asks for the 100 nearest vectors with `status = 'scheduled'` and the date window, and D1 applies the other filters. Vectorize's scores are approximate, so the survivors are scored again by exact cosine similarity from their stored vectors (`getByIds`, 20 ids a call), and those above 0.2 are kept in that order. Whoever writes an event's status or start time must update its vector's metadata too.
- **List filters** reach SQL as one JSON array each, read with `json_each(?)`, so no query nears D1's limit of 100 bound values.
- **Venue similarity.** [`trigram.ts`](../src/shared/lib/search/trigram.ts) is a port of pg_trgm `similarity()`. The committed `trigram.fixture.json` records agreement with the old database on 500 name pairs at cutover. [`venue-similarity-d1.ts`](../src/features/import/core/venue-similarity-d1.ts) has the D1 versions of `find_similar_venue` and `intake_similar_venues`. The importers and the intake switch to them with their D1 repositories in delivery PR 04 and PR 06.

## Writing from server code

[`src/shared/lib/db/d1.server.ts`](../src/shared/lib/db/d1.server.ts) is the seam the later PRs build on.

- **`boundD1Database(env)`** returns the `DB` D1 binding of a Worker env or SvelteKit `platform.env`, or `null` when there is none. Callers use the binding or refuse the operation.
- **`batchAssert(db, reason, condition, ...values)`** makes a statement for a `db.batch()`. If `condition` is false, the whole batch is rolled back and fails with `reason`. It works through the `_assert` table, whose rows are never kept.
- **`commitIntakeEvent` in `src/shared/lib/db/event-write.ts`** runs the intake checks, catalog patch, evidence, and receipt in one batch. The gateway opens and clears `write_context` inside that transaction so intake can change protected facts. A failed batch leaves no bypass behind. Hand-written fixes must likewise put the bypass setup, writes, and cleanup in the same transaction.

## Tests

[`tests/support/d1.ts`](../tests/support/d1.ts) `freshD1()` starts an in-memory Miniflare D1 through Wrangler's `getPlatformProxy`. It applies every file in `migrations/` in order. Call it once per test file in `beforeAll`, and call `dispose()` in `afterAll`. Run it under Vitest on Node with `bun run test`. It needs no credentials. Miniflare enforces D1's real SQL authorizer and foreign keys. Standalone fuzzing and local diagnostics on Bun still use the bounded retry for Bun's workerd control-pipe failures.

Run `bash scripts/test-d1-db.sh` for the local delivery database gate. It exercises schema constraints and triggers, search, catalog, chat, auth, and intake against Miniflare without Docker or credentials.

## Chat, guests, Telegram, feedback, and the rate limiter (PR 05)

[`src/shared/lib/db/d1-binding.server.ts`](../src/shared/lib/db/d1-binding.server.ts) holds the Worker's `DB` binding. The SvelteKit hook and the Telegram Worker's `fetch`, `alarm`, and `scheduled` record it with `useD1Binding(env)`, together with search's `useCloudflareBindings(env)`, so a Telegram turn stores and searches on the same backend. The jobs Worker's guest retention step reads the binding from its env directly. These paths require D1.

- **Chat turns.** [`chat-d1.server.ts`](../src/features/chat/api/chat-d1.server.ts) ports `bootstrap_chat_turn`, `claim_chat_turn`, `complete_chat_turn`, `fail_chat_turn`, and `insert_message_with_turn` to single `db.batch()` calls. Row locks become `batchAssert` preconditions and guarded `UPDATE … WHERE`. Sequence and turn numbers are computed inside the insert statement, so concurrent writers can't share one. The error messages are the RPCs' own (`Turn conflict`, `Turn claim lost`, and so on).
- **Ownership.** D1 has no row-level security. Every chat function takes the signed-in user's id (from `event.locals.user`, which the session hook sets) and filters by it. Telegram's conversations have no user and are reached only through the `telegram` channel with `user_id IS NULL`.
- **Conversation search** matches every word of the query as a case-insensitive substring of a message, instead of Postgres' `websearch_to_tsquery`. The match runs in JavaScript over the user's own messages, because SQLite's `lower()` folds only ASCII and would miss "Ópera". That is enough for a few dozen conversations.
- **Rate limiter.** [`rate-limit-d1.server.ts`](../src/shared/lib/db/rate-limit-d1.server.ts) counts with one `INSERT … ON CONFLICT DO UPDATE … RETURNING` and deletes windows older than 7 days in the same batch. Chat stays at 50 an hour and the API at 10 a minute, and it still fails closed (3-second ceiling, then 503 or a chat error).
- **Guest lifecycle and debug rows, `/api/feedback`, and Telegram's `telegram_updates`, retention, and health** persist their rows on D1.
- **Checking against staging data.** `node scripts/check-chat-d1-staging.ts` runs the chat, Telegram, and feedback readers against `baeventos-staging` through a wrapper that refuses anything but SELECT. It then exports the chat tables into a local Miniflare D1 and runs the write paths on the copied rows there. It prints counts only and exits 1 on any failure.
- **Sessions.** On a D1-bound Worker the session comes from Better Auth (next section).

## Sign-in and user data (PR 07)

Better Auth 1.7 handles magic links and Google. `/api/auth/*` returns 503 without `DB` or `AUTH_SECRET`.

- **Tables.** [`migrations/0004_better_auth.sql`](../migrations/0004_better_auth.sql) adds `users`, `sessions`, `accounts`, `verification_tokens`, and `auth_rate_limits`. `users.id` is the id that `profiles`, `saved_events`, `user_preferences`, and `conversations` key on. Inserting a user creates its profile (as Supabase's auth trigger did). Deleting a user deletes the profile, which cascades to the user's saved events, preferences, and conversations.
- **Server.** [`better-auth.server.ts`](../src/features/auth/api/better-auth.server.ts) builds Better Auth for each request from the Worker env: `DB`, the secret `AUTH_SECRET`, the `send_email` binding `EMAIL`, and optionally `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. A D1 Worker without `AUTH_SECRET` signs nobody in, and `/api/auth/*` answers 503. Sessions last 30 days in the cookie `baeventos.session_token`, with a signed 60-second cookie cache, so a sign-out or role change reaches other devices within a minute. Magic links last 15 minutes, work once, and are stored hashed. Requests are limited to 5 a minute per IP address (from `cf-connecting-ip`).
- **Email.** [`magic-link-email.server.ts`](../src/features/auth/api/magic-link-email.server.ts) sends the link from `BA Eventos <accounts@baeventos.com>` through `EMAIL`, in Spanish or English by the sign-in page's locale. Its HTML follows `docs/supabase-magic-link-email-template.html`. The binding must list `accounts@baeventos.com` in `allowed_sender_addresses`.
- **Google** links to an existing user only when Google marks the email verified and the existing user's email is verified too. No provider is trusted, because a trusted provider skips Google's own verified flag. Its callback is `https://<host>/api/auth/callback/google`, registered in the `ba-eventos` Google Cloud project.
- **Admin** is still `profiles.role = 'admin'`.
- **User data.** [`user-store.server.ts`](../src/features/auth/api/user-store.server.ts) reads and writes a user's profile, saved events, and account on D1. Every call takes the user id from the server session, because D1 has no row-level security. The browser reaches saved events through `/api/saved` and the profile through remote functions, and `/api/saved` answers 409 when the request names an `expectedUserId` that isn't the session's user.
- **Session changes in the browser.** Better Auth has no `onAuthStateChange`, so [`better-auth-session-sync.ts`](../src/features/auth/hooks/better-auth-session-sync.ts) re-reads `/api/auth/get-session` when a tab regains focus or becomes visible, and after this tab signs out or deletes its account. A magic link completed in another tab signs the original tab in when it's next shown.
- **Preserved identities.** Existing accounts retained their IDs at cutover. A returning Google user links by verified email. No legacy sessions were copied.

## Public reads (PR 07b)

Catalog reads in `client.server.ts` use `event-reads-d1.server.ts` and decode rows with search's `toPayload`. Each read selects only the fields it exposes:

- the weekly home agenda and its compact `/api/events/happening-soon` endpoint (`getHomeAgendaEvents`), the event page and the chat tools' event details and directions (`getEventWithVenue`), MCP `get_event` (`getDisplayableEventById`), the artwork lookup (`getEventArtwork`), chat follow-up facts (`getEventFactsByIds`), venue details (`getVenueById`), and `GET /api/events` (`getEventsWithVenues`).

**Artwork in R2.** Intake commits store `r2:<content type>:<sha256>.<ext>` in `events.image_url`. The catalog codec also reads the original URLs written by the D1 copy tool and earlier intake without changing those rows. Public consumers still receive `https://baeventos.com/api/event-artwork/<event id>/<sha256>.<ext>` or the unchanged external URL. The artwork route reads the key from the current reference of a displayable event and serves it through `ARTWORK` (`baeventos-artwork-staging` on staging, `baeventos-artwork` in production) with an immutable one-year cache. Its 320/640/1280 WebP variants read the same object from R2 and fall back to the original path on the current host. The private evidence bucket is not a delivery source.

Deploy catalog readers before the intake writer (the existing workflow deploys web, MCP, and chat before jobs). After intake writes references, keep a dual-format reader in any rollback; the old reader cannot serve new references.

**Event creation.** `POST /api/events` remains unavailable. Imports and the intake write through their catalog repositories.

**Acquisition cache.** Successful anonymous source observations can be reused from a bounded TTL cache on the same isolate. A retry in a fresh isolate fetches again.

**Checking event facts against production.** `node scripts/check-event-facts-staging.ts <prod-read.sh> <event id>...` runs `getEventFactsByIds` on the staging D1 (SELECT only) and compares it with the same projection of production's rows read through the GET-only `prod-read.sh`. It exits 1 on any difference.

## Catalog

The importers, venue settlement, the venue review queue, enrichment, the blocklist, and the daily-scrape audit write through one repository, `CatalogStore` (`src/features/import/core/catalog-store.ts`). `catalogStoreFor(env)` requires both `DB` and `VECTORIZE`, because new events would be unsearchable without the index.

- **Decoding.** `catalog-store-d1.ts` decodes rows with Effect Schema (0/1 to booleans, JSON text to arrays and objects) and writes every timestamp with `toISOString()`. Inserts generate the id with `crypto.randomUUID()`.
- **Venues.** Same-name and fuzzy matching run over the venue list. The store keeps the list in memory, and before each lookup it reloads the list if the count, the newest rowid, or the newest `updated_at` of `venues` changed. That way a venue that one source's import creates is seen by the others, which run concurrently. Inside the list, `venueNameKey` replaces `venues_named`, and `trigramSimilarity` (`src/shared/lib/search/trigram.ts`, delivery PR 03) replaces `find_similar_venue`, with the same tie-break (oldest, then lowest id).
- **Vectorize.** The vector id is the event id, and its metadata is `{ status, starts_at }`, with `starts_at` in epoch ms. An event write with a new embedding upserts the vector. A write that changes `status` or `starts_at` rewrites the metadata and keeps the values, because Vectorize has no metadata-only update. When intake protection reverts the search document, the old vector stays, as the old embedding did in Postgres. Deleting events deletes their vectors. The D1 write comes first. A write with a new embedding also adds the event to `vector_sync` (`migrations/0003_vector_sync.sql`) in the same transaction, and removes it once Vectorize has the vector. If the Vectorize call fails, the event stays queued.
- **`mark-past-events`.** The hourly cron in `baeventos-jobs` (`src/jobs-worker/catalog-maintenance.ts`) marks ended events `past` and updates the vector's status. All-day and time-TBA events with explicit ends cannot become `past` before their Buenos Aires start day is over. Without an explicit end, the fallbacks are 4 hours after a timed start and 28 hours after a date-only start.
- **Nightly reconcile.** At 03:00 Buenos Aires, it runs `reembed-stale` for scheduled events with an old or missing search document (queued in `vector_sync` the same way). It re-embeds each event still in `vector_sync` from its stored `search_document`, restores missing vectors of live events from their stored document, and rewrites metadata that differs from the row. Metadata-only publisher corrections queue in `vector_metadata_sync` and reuse existing vector values; they do not replace outstanding document repairs. It checks every event that isn't past or canceled, plus every event changed in the last 48 hours. At most 200 embedding calls run per night, and the rest is reported as `deferred`.
- Both crons skip when `DB` is missing and refuse to run without the matching `VECTORIZE` index.

## Operator commands

- `bun run instagram:intake --help`: offline command list. Real commands require `INTAKE_API_URL` and `INTAKE_API_TOKEN`; see [intake](instagram-intake.md).
- `bun run source:health [--staging]`, `bun scripts/guest-chat-debug.ts <id> [--staging]`, and `bun run snapshot:search-corpus [--staging] [--limit N]` use `bin/ba-d1-read.sh`. Configure `BA_D1_TOKEN_FILE` with a D1 Read token. The default is `~/.config/ba-events/cloudflare-deploy-token`. Reads default to production; `--staging` selects staging. The snapshot's `--fixture` mode needs no database. Guest transcripts are private.
- `bun scripts/populate-embeddings.ts --staging|--production [--limit N]` repairs missing vectors across event statuses, checking actual index membership. It uses the stored search document when possible.
- `bun scripts/reembed-stale.ts --staging|--production [--limit N]` rebuilds scheduled events with an old embedding version or missing document in `(starts_at, id)` order. Both repair commands allow 1–200 items per run (default 200) and submit an asynchronous Workflow using the selected jobs config. Inspect the printed instance ID for completion, errors, whether more rows remain, and any writes blocked by intake protection. They refuse `DB_READ_ONLY=1`; they are separate from the nightly reconciliation.
